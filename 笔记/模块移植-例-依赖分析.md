## ❗️注意 

此方法只能保证当前替换的函数能工作，不保证其他未分析的函数能工作, 也不保证逻辑的一致性, 仅为理想情况。
现实情况多为通过梳理两个模块的(`隐式`和`显示`)依赖关系并读函数名语义来替换(`全局思考` + `信任命名`)

---
## 一、只替换一个函数

假设我们有**模块A**和**模块B**，当前只关心**Read**函数，**其他函数暂不考虑**。

### 模块A（原模块）
```cpp
int g_ready = 0;

int Init() {
    g_ready = 1;
    return 0;
}

int Read() {
    if (!g_ready) return -1;
    return 0;
}
```

### 模块B（新模块）
```cpp
int Read() {
    return 0;   // 不依赖任何前置条件
}
```

**对比依赖**：
- D(Read_A) = {g_ready 必须为 1}
- D(Read_B) = ∅

∅ ⊆ {g_ready 必须为 1} ✅ **满足局部替换条件**（B的依赖比A少）。

**贪心策略**：既然Read不再需要`g_ready`，直接将`Init`函数体清空。

```cpp
int Init() {
    // 空实现
    return 0;
}
```

此时，替换后的`Read`工作正常。

## 二、后续发现：其他函数也依赖`Init`

假设几天后，在代码的更远处发现`Write`函数也需要`Init`设置的状态：

### 模块A（原模块）
```cpp
int Write() {
    if (!g_ready) return -1;   // 同样依赖 g_ready
    return 0;
}
```

### 模块B（新模块）
```cpp
int g_connected = 0;

int Write() {
    if (!g_connected) return -1;   // 依赖 g_connected
    return 0;
}
```

我们发现对于`Write`函数, 它们有相同的依赖结构。

**贪心策略**：既然`Write`也需要`Init`设置的状态。

```cpp
int Init() {
    g_connected = 1;
    return 0;
}
```
由于`Read`函数不需要`g_connected`, 这样改动不会影响`Read`。

## 四、局部公式与贪心边界

**局部公式**（只看替换的目标函数）：  
D(F_B) ⊆ D(F_A) → 可替换。

**贪心策略**：当局部替换满足条件时，优先最小改动（如Nop掉被依赖的函数）。  
**但该策略是局部的**，不保证其他未分析的函数不受影响。后续发现新冲突时, 需回溯修正。
