
### 📝 补充说明：不创建 `DRIVER_OBJECT` 的情况

笔记中描述的“I/O管理器为每个驱动创建 `DRIVER_OBJECT`”这一规则，有一个重要前提：**驱动是通过Windows标准的加载机制（如SCM的`StartService`）加载的**。

如果驱动通过以下**非常规方式**加载，就不会有标准的 `DRIVER_OBJECT`：

*   **`ZwSetSystemInformation` + `SystemLoadAndCallImage`**：这是一个未文档化的系统调用，它只能将一个**普通内核模块**加载到内存并调用其入口点，**不会为其创建 `DRIVER_OBJECT`**。这种方式加载的模块无法调用 `IoCreateDevice` 等标准驱动API，常被Rootkit用于隐蔽加载。

*   **手动映射 (Manual Mapping)**：这是一种更底层的技术，由攻击程序（如`kdmapper`）在已获得的内核权限下，手动将驱动文件解析并复制到内核内存中，**完全绕过了Windows的加载器**，因此**不会产生任何 `DRIVER_OBJECT` 或注册表项**。

这些非常规方式加载的模块没有标准的 `DRIVER_OBJECT`，因此在 `driverquery` 或 WinObj 等工具中不可见，分析难度也更高。

基于以上分析，这是整合了例外情况的修订版笔记：

### Windows 内核驱动模型笔记（修订版）

### 1. 静态结构：驱动、设备和对象管理器

`DriverEntry_0` 函数的核心工作，就是填充两个关键数据结构，并与系统的“对象管理器”交互。

#### 🔹 `DRIVER_OBJECT`（驱动对象）

驱动的“身份证”。系统为每个通过**标准方式加载**的驱动创建并维护这个结构，记录驱动的全部元信息：

*   驱动的起始地址、大小
*   卸载函数指针（`DriverUnload`）
*   指向 `DEVICE_OBJECT` 链表的指针
*   **`MajorFunction`** 函数表：一个函数指针数组，索引对应不同的 I/O 请求类型（IRP）。它就是告诉系统“当某类请求到来时，调用我的哪个函数”。

> **例外情况**：通过 `ZwSetSystemInformation` 或“手动映射”等非常规方式加载的内核模块，**不会**被分配 `DRIVER_OBJECT`。

#### 🔹 `DEVICE_OBJECT`（设备对象）

驱动的“实体办公室”。`IoCreateDevice` 创建的就是它，代表一个具体的设备实例。

关键成员：
*   **`DriverObject`**：指回创建它的 `DRIVER_OBJECT`。
*   **`NextDevice`**：指向同一驱动创建的下一个设备对象，形成链表。
*   **`DeviceExtension`**：驱动私有的扩展空间。

> ⚠️ 本例中 `IoCreateDevice(DriverObject, 0, ...)` 的第二个参数传的是 `0`，表示没有申请设备扩展空间。

#### 🔹 `DRIVER_OBJECT` 与 `DEVICE_OBJECT` 的关系

一个驱动可以管理多个设备对象。`DRIVER_OBJECT` 通过 `DeviceObject` 指针指向链表头，串联所有下属设备。

I/O 请求的最终目标总是某个具体的 `DEVICE_OBJECT`，而不是直接发给 `DRIVER_OBJECT`。

#### 🔹 对象管理器（Object Manager）与命名空间（Namespace）

Windows 内核用一个树状结构来管理所有内核对象，叫**对象管理器命名空间**。它就像系统的“内核文件系统”，根是 `\`，统一管理设备、文件等对象的“可见性”。

你代码里这两个路径就是命名空间中的节点：
*   `\Device\Cracker`：设备对象在内核空间的“门牌号”
*   `\DosDevices\Cracker`：符号链接，让用户态可以通过 `\\.\Cracker` 访问

创建流程：
1.  `IoCreateDevice`：在 `\Device` 下创建设备对象
2.  `IoCreateSymbolicLink`：在 `\DosDevices` 下创建符号链接指向它

用户态访问路径：`\\.\Cracker` → `\DosDevices\Cracker` → `\Device\Cracker`

### 2. 动态行为：I/O 请求包（IRP）

有了静态结构，驱动才能处理请求。

当用户态调用 `DeviceIoControl` 时，I/O 管理器创建一个 **IRP（I/O Request Package）**，像快递单一样携带请求信息，逐层转发：

1.  通过对象管理器在命名空间中找到 `\\.\Cracker`，定位到 `DEVICE_OBJECT`
2.  通过 `DEVICE_OBJECT->DriverObject` 找到 `DRIVER_OBJECT`
3.  从 `DRIVER_OBJECT->MajorFunction[14]` 取出处理 `IRP_MJ_DEVICE_CONTROL` 的函数指针
4.  调用该函数（本例中为 `sub_1000`）处理请求

### 3. 内存布局：驱动住在哪？

驱动运行在**内核模式**，位于系统内核地址空间。

在 x64 Windows 中，虚拟地址空间分为两部分：
*   **用户地址空间（低区）**：每个进程私有，存放用户态程序
*   **系统地址空间（高区）**：所有进程共享，存放 Windows 内核、HAL、所有内核驱动

> ⚠️ 在 64 位系统下，这个分区比例远比 32 位下的“低 2GB/高 2GB”复杂，但“所有进程共享高区”这个核心原理不变。

驱动存在于高区，因此拥有访问任何进程内存的最高权限。

### 💎 总结：完整流程

1.  **驱动被加载时**（通过标准 SCM 方式），I/O 管理器为它创建一个 `DRIVER_OBJECT`。
2.  **`DriverEntry` 执行时**：
    *   调用 `IoCreateDevice` 在对象管理器命名空间的 `\Device` 下创建 `DEVICE_OBJECT`
    *   调用 `IoCreateSymbolicLink` 创建 `\DosDevices\Cracker` 让用户态程序可以找到它
    *   填充 `DRIVER_OBJECT->MajorFunction` 表，告诉系统各类 IRP 由哪个函数处理
    *   设置 `DriverUnload`，指定卸载时的清理函数
3.  **用户态调用 `DeviceIoControl` 时**：
    *   I/O 管理器构造 IRP
    *   通过命名空间找到 `\\.\Cracker`，定位到 `DEVICE_OBJECT`
    *   通过 `DEVICE_OBJECT->DriverObject` 找到 `DRIVER_OBJECT`
    *   从 `MajorFunction[14]` 取出函数指针，调用 `sub_1000` 处理请求

**核心理解**：驱动初始化的本质，就是在内核中搭建一套“静态结构”（对象 + 函数表），让系统能够在动态行为发生时（IRP 到达），正确地路由到你的处理函数。你之前把 `MajorFunction` 比作中断向量表，这个直觉是完全正确的——它就是这个路由机制的核心。

> **补充**：上述模型适用于通过标准服务管理器（SCM）加载的驱动。通过 `ZwSetSystemInformation` 或手动映射等非常规方式加载的内核模块，不会创建 `DRIVER_OBJECT`，因此也无法使用标准驱动API，常见于Rootkit等需要隐蔽性的场景。
