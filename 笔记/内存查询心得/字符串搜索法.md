### 字符串搜索法：逆向工程核心笔记（精简完整版）

#### 1. 引言：本质与价值
字符串搜索法是逆向分析的起点，其本质是**通过可读文本线索，快速定位程序功能逻辑**。在多数情况下，程序中的提示信息、错误消息、路径、URL等均以明文或易解码形式存在，是破解关键算法、分析恶意行为的突破口。

---

#### 2. 静态搜索法（适用80%常规场景）
**原理**：直接扫描二进制文件（PE/ELF）中连续的可打印字符序列。

**操作步骤**：
1.  **提取**：使用IDA/Ghidra的"Strings"子窗口，或Linux命令`strings 文件名 > output.txt`。
2.  **筛选**：聚焦于有业务含义的词汇，如`"Wrong"`、`"Grant"`、`"http"`、`"password"`。过滤编译器生成的杂项（如`@_NULL_IMPORT`）。
3.  **定位**：对候选字符串使用**交叉引用（XREF）**，跳转到引用该字符串的汇编代码处，分析周围逻辑。

---

#### 3. 静态搜索的“两大坑”与解法

##### 坑1：碎片化字符串（编译优化导致）
- **现象**：关键字符串被编译器拆成多段散落在不同地址，直接搜完整句子搜不到。
- **示例**：代码中`"Please enter password"`可能被拆分为`"Please "` + `"enter "` + `"password"`。
- **解法**：放弃完整句，**搜索最有特征的单词碎片**（如`"pass"`或`"enter"`），通过XREF找到拼接代码块（通常伴随`strcat`/`sprintf`调用）。

##### 坑2：编码问题（Unicode/ASCII混淆）
- **现象**：在内存窗口看到`E.n.t.e.r`（每个字母间有`00`），这是因为使用了**UTF-16 LE编码**。若直接搜ASCII字符串"Enter"会失败。
- **原理**：`'E'`的UTF-16表示为字节对`45 00`，ASCII视图显示为`E.`。
- **解法**：
    - 静态分析：在IDA/Ghidra中切换字符串编码格式（通常有ASCII/Unicode选项）。
    - 动态分析：在x64dbg内存搜索框中，明确勾选"Unicode"选项，而非默认的"ASCII"。

---

#### 4. 动态场景（静态失效时的转型策略）
当上述方法无果，说明字符串可能在运行时才生成或加载，此时必须切换为**动态追踪**。

##### 场景A：外部翻译文件/资源包
- **特征**：程序支持多语言，文本存储在`.ini`、`.json`、`.mo`或独立的`.dll`资源中。
- **静态盲区**：主程序中没有目标文本。
- **定位逻辑法（推荐）**：
    1. 对API下断点：`LoadStringW`（Win32）、`FindResource`、`ReadFile`（读取外部文件）。
    2. 程序运行时断下，查看调用栈（Call Stack），回溯至主程序调用此API的代码区域。
    > **核心思路**：不找字符串，找**加载字符串的函数入口**，从而定位逻辑。

##### 场景B：动态拼接生成
- **特征**：URL、日志信息由固定前缀与变量（如用户名、时间戳）拼接而成。
- **静态盲区**：完整的最终字符串不存在于文件。
- **解法**：
    1. 静态备选：搜索固定前缀片段（如`"https://"`或`"api."`）。
    2. 动态截获：在拼接函数（`sprintf`、`strcat`、`Format`）下断点，执行后查看目标缓冲区的内存内容。
    > **核心操作**：在调试器的"内存窗口"中监视缓冲区地址，即可看到最终生成的完整字符串。

---

#### 5. 总结：以“逻辑”为核，变通为魂
| 场景 | 症状 | 对策 |
| :--- | :--- | :--- |
| **静态明文** | 直接搜到完整句子 | XREF跳转，分析代码 |
| **静态碎片** | 搜完整句失败，但能搜到单词 | 搜索特征单词，找拼接指令 |
| **编码异常** | 显示`E.n.t.e.r` | 切换Unicode搜索模式 |
| **外部资源** | 主程序搜不到任何文字 | 断点`LoadString`/`ReadFile`，回溯调用栈 |
| **动态拼接** | 字符串内容在运行时变化 | 断点`sprintf`/`strcat`，监视内存缓冲 |

**终极心法**：字符串只是路标，而非终点。当路标被藏起或拆散时，就去拦截**建造路标的工人（API/拼接函数）**。学会在静态搜索无果时迅速切换动态调试，是逆向能力进阶的标志。

### 适用条件

并不是所有程序都适合一上来就搜字符串。如果不满足以下条件，你可能会浪费大量时间在无意义的乱码上。请按优先级自检：

#### ✅ 最佳适用场景（成功率 > 80%）
1. **程序未加壳，或仅压缩壳（如 UPX）**：这是硬性门槛。加壳相当于把程序整体加密压缩，字符串会被打乱。若用 PE 查看工具（如 Exeinfo PE）检测到 `UPX` 或 `ASPack`，需先**脱壳**再搜；若检测到强壳（如 VMP、Themida），静态字符串搜索基本无效，请直接转入动态调试。
2. **字符串以标准 C 风格存储**：即 ASCII 或 UTF-16 LE 编码，以 `\0` 结尾。大多数传统 Win32 程序符合此条件。
3. **目标功能存在固定的提示文本**：比如登录框有“Login”、错误框有“Error”、设置窗口有“Configuration”。

#### ⚠️ 需转换条件的场景（成功率中等）
4. **.NET 或 Java 程序**：字符串通常存储在元数据或常量池中。IDA 直接打开可能看不到，需用专用工具（如 `dnSpy` 或 `JD-GUI`）查看，或在内存中搜索 UTF-16 编码。
5. **Go 语言程序**：Go 的字符串不是以 `\0` 结尾，且无固定数据段。直接 `strings` 命令通常无效，需在内存窗口搜索**非空终止的连续字节序列**，或使用专门分析 Go 二进制文件的插件。
6. **中文字符串**：汉字通常采用 UTF-16 LE（如 `D6 D0` 代表 "中"），若搜索时勾选 ASCII 必定失败。务必在工具中切换为 Unicode 搜索模式。

#### ❌ 完全无效的场景（不必浪费时间）
7. **字符串经过强加密/混淆**：即使脱壳后，关键字符串也被开发者用 XOR、Base64、RC4 等算法加密存储在数据段。此时搜出来的全是乱码。需动态调试，等程序解密后再在内存中抓取。
8. **纯动态生成且无固定碎片**：比如程序从网络 API 实时拉取提示语，或所有文本来自数据库。此时搜索本地文件毫无意义，应直接断点网络函数或数据库读取函数。

### 快速自检清单（开始搜索前问自己）

| 检查项 | 通过标准 | 若不通过，替代方案 |
| :--- | :--- | :--- |
| **加壳检测** | Exeinfo PE 显示 "Not packed" 或 "UPX" | 脱壳，或直接上动态调试 |
| **编码确认** | 目标文字在内存中显示为正常英文/汉字 | 切换 ASCII/Unicode 搜索模式 |
| **语言特性** | 传统 C/C++ 程序 | .NET用dnSpy，Go用特定插件 |
| **明文可见** | 用 `strings` 命令能扫出少量英文单词 | 考虑程序是否对关键文本做了加密 |
