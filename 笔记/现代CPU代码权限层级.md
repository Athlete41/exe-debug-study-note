## 1. 硬件层级远不止 Ring 0~3

之前的笔记介绍了 **Ring 0 ~ Ring 3**，并补充了 **Ring -1（Hypervisor）** 和 **Ring -2（SMM）**。

但现代 x86 处理器（Intel / AMD）在硅片层面实际上内置了 **至少 6 个独立的特权运行环境**，从用户态一直延伸到芯片内部的独立微控制器。

> **核心事实：** 这些层级全部由 **CPU 硬件原生支持**，不是软件模拟出来的。每一个层级都有独立的寄存器、内存空间和中断处理逻辑，部分层级甚至拥有独立的 CPU 核心（如 ME / PSP）。

---

## 2. 完整层级对照表（从最高权限到最低权限）

| 层级 | 官方名称 | 运行者 | 硬件支持来源 | 是否对 OS 透明？ | 典型用途 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Ring -3** | **管理引擎 / 平台安全处理器** | Intel ME / AMD PSP | CPU 内部独立的 **ARC/ARM 核心** | **完全透明**（OS 看不到） | 初始化、远程管理、DRM、安全启动 |
| **Ring -2** | **系统管理模式 (SMM)** | UEFI/BIOS 固件代码 | CPU 原生支持的 **SMI 中断机制** | **完全透明**（OS 不可访问 SMRAM） | 电源管理、硬件错误处理、固件更新 |
| **Ring -1** | **虚拟机根模式 (VMX Root)** | Hypervisor（VMM） | Intel **VT-x** / AMD **AMD-V** | 部分透明（OS 知道自己被虚拟化） | 虚拟机监控、VBS/HVCI 安全隔离 |
| **Ring 0** | **内核态** | 操作系统内核 | x86 原生 **4 个 Ring 级别** | OS 自己管理 | 内存管理、进程调度、设备驱动 |
| **Ring 1** | **中间层（极少用）** | 设备驱动（历史） | 同 Ring 0 | OS 自己管理 | 现代操作系统几乎不用 |
| **Ring 2** | **中间层（极少用）** | 设备驱动（历史） | 同 Ring 0 | OS 自己管理 | 现代操作系统几乎不用 |
| **Ring 3** | **用户态** | 应用程序 | 同 Ring 0 | OS 自己管理 | 普通软件运行 |

## 3. 每一层的硬件实现细节（重点）

### 3.1 Ring 0 ~ Ring 3：x86 原生特权环（CPL）

-   **硬件机制：** 代码段寄存器 **CS（Code Segment）** 的低 2 位存储了当前特权级（CPL，Current Privilege Level）。CPU 执行任何指令前，都会检查 CPL 是否满足指令所需的特权级别。
-   **Gate 门机制：** 通过 **调用门（Call Gate）**、**中断门（Interrupt Gate）** 和 **任务门（Task Gate）** 实现跨 Ring 的控制转移。
-   **这是 Intel 80386 时代就内置的硬件设计，至今未变。**

### 3.2 Ring -1：VT-x 根模式（硬件虚拟化）

-   **硬件机制：** 引入了一个新的 CPU 模式标志 **VMX（Virtual Machine Extensions）**。通过执行 `VMXON` 指令开启，`VMLAUNCH` / `VMRESUME` 指令切换虚拟机。
-   **新增控制结构：** **VMCS（Virtual Machine Control Structure）**，这是一块由 CPU 硬件管理的特殊内存区域，存储了 Guest 状态、Host 状态和 VM-Exit 触发条件。读写 VMCS 有专用指令（`VMREAD` / `VMWRITE`）。
-   **VM-Exit 由硬件自动触发：** 当 Guest 执行敏感指令（如 `CPUID`、`IN/OUT`、`MOV CR3`）或发生外部中断时，**CPU 硬件自动保存 Guest 上下文、加载 Host 上下文、跳转到 Hypervisor 入口**。全程零软件介入。

### 3.3 Ring -2：SMM（系统管理模式）

-   **硬件机制：** 当 CPU 收到 **SMI（System Management Interrupt，系统管理中断）** 引脚信号时，硬件自动执行以下操作：
    1.  保存当前所有寄存器到 **SMRAM**（一块特殊物理内存）。
    2.  切换到一个独立的地址空间（SMM 模式）。
    3.  跳转到 SMRAM 中的 BIOS 入口地址执行 SMM 代码。
    4.  执行 `RSM`（Resume from SMM）指令恢复寄存器。
-   **关键硬件特征：** SMRAM 在非 SMM 模式下**完全不可见**，即使 Ring 0 的操作系统也无法读写。这是由 **芯片组硬件** 实现的地址范围锁定。

### 3.4 Ring -3：Intel ME / AMD PSP（平台安全处理器）

这是最底层的硬件特权层，实际是一个运行在 **CPU 内部独立微控制器** 上的小型操作系统。

-   **Intel ME（Management Engine）：** 一个运行在 Intel CPU 内部的 **ARC 架构 32 位 RISC 处理器**，拥有独立的 ROM、RAM、时钟和网络协议栈。它在电脑通电但 CPU 尚未启动时就开始运行。
-   **AMD PSP（Platform Security Processor）：** 一个运行在 AMD CPU 内部的 **ARM Cortex-A5 核心**，功能与 Intel ME 对标。
-   **独立于主 CPU：** 主 CPU（x86 核心）完全看不到 ME/PSP 的内存和寄存器。ME/PSP 可以访问物理内存（通过 DMA）、管理网络流量（内置 MAC 地址）、甚至在系统关机时保持活动。
-   **权限范围：** 它可以**覆盖**主 CPU 的指令执行，例如在安全启动过程中验证 UEFI 固件签名，若验证失败则直接阻止主 CPU 启动。

## 4. 安全视角：攻击者如何逐级攻破硬件层级？

```
  Ring  3  → 普通恶意软件（最容易攻击）
      ↓  提权漏洞
  Ring  0  → 内核级 Rootkit（需要驱动签名绕过 / 0day）
      ↓  虚拟机逃逸漏洞
  Ring -1  → Hypervisor 级后门（国家级 APT 水平）
      ↓  SMM 缓冲区溢出（极罕见，需要物理或固件写权限）
  Ring -2  → SMM 固件植入（永固性后门，重装系统无法清除）
      ↓  ME/PSP 固件漏洞（几乎不可检测，NSA 级别）
  Ring -3  → ME/PSP 后门（完全控制硬件，连电源键都归它管）
```

> **为什么 Ring -3 是最可怕的？**
> 因为 Intel ME 运行在独立的微控制器上，拥有自己的网卡（iAMT），甚至在系统关机时仍可保持联网。如果 ME 被植入后门，攻击者可以：
> - 在操作系统完全关闭的情况下远程开机、远程重装系统。
> - 绕过所有操作系统层面的安全软件（杀毒软件看不到它）。
> - 读取所有物理内存（包括加密密钥），因为 ME 有 DMA 能力。
> - 该后门无法通过重装系统、换硬盘、甚至换主板（除非换 CPU 型号）清除。

## 5. 为什么这些层级普通开发者接触不到？

| 层级 | 访问方式 | 普通开发者能碰吗？ |
| :--- | :--- | :--- |
| Ring 0 | 写 Windows/Linux 内核驱动 | ✅ 可以（但需要签名和特权） |
| Ring -1 | 通过 Hyper-V / KVM 的 API | ✅ 间接可以（通过虚拟化 SDK） |
| Ring -2 | 需要刷写 UEFI/BIOS 固件 | ❌ 极少数固件工程师 |
| Ring -3 | 需要 Intel/AMD 专属固件开发工具 | ❌ 只有芯片厂商和 OEM 合作方 |

**Ring -3 的开发者文档是锁在 Intel/AMD 内部保险柜里的，对外不公开。** 这就是为什么安全研究员花了 10 多年才逆向出 ME 的内部架构（如 2017 年的 Intel ME 漏洞 CVE-2017-5689）。
