> **适用范围**：以下以 x86/x64 Windows + MSVC/MinGW 工具链为例，描述从源码到 `.exe` 的编译链接过程。编译四阶段本身与架构无关，但此处侧重 Windows 平台上的工具链与产物形态（`.obj` → `.exe`）。

---

### 编译四阶段

| 阶段 | 工具（MSVC） | 工具（MinGW） | 输入→输出 | 地址形态 |
|:---|:---|:---|:---|:---|
| **1 预处理** | `cl /E` | `gcc -E` | `.c` → `.i` | **无地址概念**（纯文本替换，展开 `#include`/`#define`） |
| **2 编译** | `cl /c` | `gcc -S` | `.i` → `.asm` / `.s` | **仅有符号**（函数调用暂填 0，留待链接器修正） |
| **3 汇编** | `ml`/`ml64` | `as` | `.asm` → `.obj` / `.o` | **可重定位地址**（各 `.obj` 段内偏移从 0 开始） |
| **4 链接** | `link` | `ld` | `.obj` + `.lib` → `.exe` | **绝对虚拟地址**（PE 加载到内存后的 VA/RVA） |

**关键认知**：前三阶段不产生最终地址。链接器不仅负责"合并段、算地址"，还负责**生成 PE 文件格式**——即组装 DOS 头、PE 头、节表和各个节。

---

### 各阶段详解

#### 1. 预处理（Preprocessing）

```
.c 源码
  │  #include 展开（头文件递归插入）
  │  #define 宏替换
  │  #if/#ifdef 条件编译剪裁
  │  注释删除
  ▼
.i 纯 C 文件（无宏、无 #include 指令）
```

此时**完全没有地址概念**，纯粹是文本操作。

#### 2. 编译（Compilation）

```
.i 纯 C 文件
  │  词法分析 → 记号流
  │  语法分析 → 抽象语法树（AST）
  │  语义分析 → 类型检查
  │  中间代码生成 → 优化 → 寄存器分配
  ▼
.asm / .s 汇编文件
```

**地址形态**：生成的汇编代码中，函数调用和全局变量引用仍以符号（`jmp func` / `call func`）表示，func 的实际地址尚未确定，汇编器会在目标文件中留空，填入暂定值（通常是 0），后续由链接器修正。

> 与 Cortex-M 相比，x86/x64 此时没有 `.s` 和 `.c` 混编的启动文件——启动代码（`crt0`/`crtbegin`）由编译器工具链自动提供，在链接阶段参与。

#### 3. 汇编（Assembly）

```
.s 汇编文件
  │  指令助记符 → 机器码
  │  生成 COFF 目标文件格式
  ▼
.obj（MSVC）或 .o（MinGW）目标文件
```

**COFF 目标文件结构**（`.obj` / `.o`）：

```
┌──────────────────┐
│  COFF Header     │  ← 机器类型、符号表位置、节数量
├──────────────────┤
│  Section Table   │  ← 描述各段信息（.text、.data 等）
├──────────────────┤
│  .text           │  ← 机器码（段内偏移从 0 开始）
│  .data           │  ← 已初始化全局变量
│  .debug$T        │  ← 调试信息（PDB 相关）
├──────────────────┤
│  Symbol Table    │  ← 所有符号（函数名、全局变量名）及其段内偏移
├──────────────────┤
│  Relocation      │  ← 重定位条目：记录哪些位置需要链接器修正地址
│  Directives      │
└──────────────────┘
```

**地址形态**：各段内偏移从 0 开始，符号表中的地址是相对段起始的偏移。`call func` 的位置被记录为重定位条目，等待链接器填入最终地址。

> **多个 `.obj` 共存**：每个 `.c` 文件独立编译成各自的 `.obj`，它们互不知道对方的地址——这正是链接器要解决的核心问题。

#### 4. 链接（Linking）

```
.obj（多个）+ .lib（静态库 / 导入库）
  │  符号解析：找到每个引用的定义
  │  段合并：相同属性的段（.text 合并、.data 合并）
  │  地址分配：为每个段分配最终 RVA
  │  重定位修正：填写所有之前留空的地址
  │  生成 PE 文件结构
  ▼
.exe / .dll
```

链接器做三件核心的事：

| 任务 | 含义 | 类比 |
|:---|:---|:---|
| **符号解析** | 把 `.obj` 间的 `call func` 和 `func` 实际位置对上 | 拼图：找每块拼图的位置 |
| **段合并** | 同类型段合并为一个连续区域 | 归类：所有 .text 拼成一段连续代码 |
| **重定位** | 将符号引用改为具体地址 | 填空：把"待填"改成"0x00401000" |

**链接产物**不再是 `.obj` 那样的 COFF 文件，而是 PE 格式的 `.exe`。

---

### COFF 目标文件 vs PE 可执行文件

| 特性 | `.obj`（COFF 目标文件） | `.exe`（PE 可执行文件） |
|:---|:---|:---|
| **地址形态** | 相对偏移（各段从 0 开始） | **绝对虚拟地址**（VA/RVA） |
| **入口点** | 无（尚未确定） | 有（`AddressOfEntryPoint`） |
| **重定位信息** | 保留（等待链接器处理） | 保留但已应用（`.reloc` 用于加载时 ASLR 修正） |
| **动态链接** | 无此概念 | 有导入表、IAT（依赖 DLL） |
| **文件头** | COFF Header | DOS MZ + PE Header |
| **能直接运行吗** | ❌ 不能 | ✅ 能 |

---

### 对比：Windows EXE vs Cortex-M 原始二进制

| 特性 | Windows EXE（MSVC/MinGW） | Cortex-M（GCC/Keil） |
|:---|:---|:---|
| **链接产物格式** | PE（.exe） | ELF → 转 .hex/.bin |
| **最终代码形态** | 加载到虚拟内存执行 | 直接烧录到 Flash 物理地址执行 |
| **启动文件** | 由链接器 / 运行时库提供（`crt0`） | 手动编写 `startup_xxx.s` |
| **动态链接** | 有（通过 DLL + IAT） | **无**（全部静态链接） |
| **入口点** | `main`（由 crt0 调用） | `Reset_Handler`（硬件直接从向量表跳入） |
| **链接脚本** | 编译器内置默认脚本 | 手动编写 `.ld` 文件 |

---

### 一句话记忆

> **预编汇编链将 `.c` 依次变成 `.i` → `.asm` → `.obj`（各段相对地址），链接器做"找→拼→填"三步（符号解析 + 段合并 + 重定位）生成最终的 `.exe`。**
