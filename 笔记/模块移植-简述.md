# 模块移植核心笔记

## 一、核心理念
移植的本质不是复制代码，而是**对齐行为契约**。必须保证新模块在“运行逻辑”上与旧模块对调用者来说完全等价。

## 二、硬性条件（5 大支柱）
**此 5 条任何一条不对齐，程序必然崩溃或完全无法运行，适配器救不了。**

| 硬性支柱 | 检查内容 | 不对齐的后果 |
| :--- | :--- | :--- |
| **1. 执行模式** | 同步（阻塞） vs 异步（回调/Future） | 异步塞进同步槽位，数据未到即执行；强行转同步极易死锁。 |
| **2. 接口契约** | ① 函数签名（参数/返回值）<br>② **数据语义**（结构体对齐 `#pragma pack`、字符串编码、变量位宽）<br>③ 错误处理（错误码 vs 异常 vs `std::optional`） | 参数压栈错位；结构体成员偏移量算错导致数据全乱；异常未被捕获直接崩。 |
| **3. 内存所有权** | 谁分配（`malloc/new/栈`）？谁释放（`free/delete/自动`）？ | 释放方式不匹配导致堆损坏或内存泄漏，随机崩溃。 |
| **4. 依赖结构** | ① 是否需要前置初始化（`Init/Open`）？<br>② 是否依赖外部环境（特定 DLL、注册表、系统服务、驱动已加载）？<br>③ 是否存在隐式全局上下文？ | 调用顺序不对返回错误或崩掉；缺依赖直接无法启动。 |
| **5. 线程安全** | 有无内部锁？是否可重入？是否依赖全局/静态变量？ | 多线程冲入导致全局变量数据撕裂，访问违例崩溃。 |

## 三、软性条件（可以适配）
**不对齐不会崩，但结果可能不对或效率不同，只需在适配层做转换。**

| 软性特征 | 适配手段 |
| :--- | :--- |
| 算法逻辑差异（快排 vs 冒泡） | 保留原算法或替换实现，只要输出相同即可。 |
| 错误码数值不同（`-1` vs `0`） | 适配层加一层 `if` 映射转换。 |
| 日志/打印格式不同 | 适配层重写输出流。 |

## 四、移植六步法
1. **测绘**：画状态机、写日志插桩，摸清两个模块的动态行为。
2. **对齐硬性**：对照 5 大支柱检查，硬性不匹配则必须修改模块源码或重构调用方。
3. **适配软性**：写适配器（Wrapper）封装语法、参数格式、错误码映射。
4. **验证**：跑旧模块的单元测试，比对输入输出是否完全一致。

---

## 五、总结口诀
> **硬性五支柱，错一即崩盘；**  
> **软性任差异，适配一层挡。**  
> **先测后搬砖，契约要对齐。**
